# Phira PP 公式总览

本文汇总当前生效的 PP 计算口径。所有数值直接取自 `phira_pp/pp.py`、`phira_pp/features.py`、
`phira_pp/pipeline.py` 与 `data/difficulty_model.json`；改动代码后请同步更新本文。

---

## 一、总体公式（整合）

```
PP_单曲 = base · D^diff_exp · acc_factor · precision_factor · error_factor

  base              = ref_pp / ref_diff^diff_exp = 1000 / 18^6 = 2.9401194e-5   ← 幅度契约
  acc_factor        = ((acc − acc_floor) / (1 − acc_floor))^acc_pow   (=0 若 acc < 0.70)
  precision_factor  = 1 + precision_weight · (score − 0.5)
                      score = clamp((precision_hi − std) / (precision_hi − precision_lo), 0, 1)
  error_factor      = (1 − (bad + miss) / total_judged)^error_pow

D  ←  难度取值链（见第四节）
D  ←  D* = bias + Σᵢ wᵢ · (xᵢ − μᵢ) / σᵢ          （19 个谱面特征，见第五节）

总PP_BestN = Σᵢ₌₁..N  PPᵢ · 0.95^(i−1)            （PP 降序，osu! 官方加权）
```

- `acc` 是主权重（命中质量），`无暇度`（`std`）是**有界**的次级修正。
- **取哪条成绩**：同一谱面有多条成绩时，取 **PP 最高**的那条（不是分数最高——
  PP 由 accuracy/无暇度/漏键驱动；实测按分数取会低 286.8 PP / 1.43%，见 `project_rules.md`「成绩选择口径」）。
- **没有**独立的长度奖励：`D*` 本身已随物量/密度增长，再加会重复计分
  （且 `log_duration` 拟合权重为负 −0.63/σ，删掉它 CV 从 0.842 掉到 0.777，见 `scripts/diag_length.py`）。

## 二、顶层变量

| 符号 | 含义 | 来源 |
|---|---|---|
| `D` | 该谱**采用**的难度（定数） | 第四节取值链 |
| `acc` | 准确率 = (perfect + 0.65·good + 0.25·bad) / total | 成绩记录 |
| `acc_factor` | 准确率系数 | 计算 |
| `std` | **无暇度**（击打误差，秒） | 成绩记录（毫秒×1000） |
| `precision_factor` | 无暇度系数，幅度仅 ±4% | 计算 |
| `error_factor` | 漏键系数（bad + miss） | 计算 |
| `bad` / `miss` / `total_judged` | 坏键 / 漏键 / 有效键数 | 成绩记录 |
| `base` | 幅度基准（`ref_pp / ref_diff^diff_exp`） | 第三节 |

## 三、参数（`PPParams`）

| 参数 | 当前值 | 性质 | 依据 |
|---|---|---|---|
| `ref_pp` | 1000.0 | **展示**（无真值） | 定数 18 且全因子=1 的成绩记 1000 |
| `ref_diff` | 18.0 | **展示** | 同上（锚点） |
| `diff_exp` | 6.0 | **策略** | 实测：2.0→天地差 144，6.0→296，低难谱被挤出 top100（`scripts/sweep_diff_exp.py`） |
| `acc_floor` | 0.70 | **策略** | 以下直接归 0 |
| `acc_pow` | 4.0 | **策略** | 99%→0.873 / 98%→0.759 / 97%→0.656（`scripts/sweep_acc_pow.py`） |
| `precision_lo` | 0.01538 s | **数据** | 实测 1392 条干净成绩 p10（`scripts/calibrate_pp.py`） |
| `precision_hi` | 0.02707 s | **数据** | 实测同上 p90 |
| `precision_weight` | 0.08 | **策略（受约束）** | 须 < `(19/18)^diff_exp` 的解，否则无暇度会盖过 1.0 定数步长（`scripts/sweep_pp_params.py`） |
| `error_pow` | 3.0 | **策略（未标定）** | 尚无扫描证据，当前为初始值 |
| `STD_PLAUSIBLE_MAX` | 0.2 s | **数据** | 超过视为破测，按中性 1.0 处理 |
| `OSU_DECAY` | 0.95 | **osu! 官方** | 非自拟 |

## 四、难度取值链

| 优先级 | 条件 | 采用值 | 来源 |
|---|---|---|---|
| 1 | `ranked == True` 且定数 > 0 | **谱师定数** | Phira API |
| 2 | 在 Suonasi KV 定数表（405 张，17.0–19.3） | **社区定数 (Suonasi)** | SuonasiOS `/kv/diff` |
| 3 | 在主观定数表（148 个上架 id，17.55–18.59） | **社区定数 (主观)**，但**只作下限**：D\* 合法且更高时取 D\* | `data/subjective_diff.xlsx` |
| 4 | 其余 | **D\* 模型** | 本模型；预测落在 [0, 20]（±0.05 容差）之外则**剔除并计数**（`dstar_out_of_range`） |

- 优先级 2 / 3 由 `phira_pp.pipeline.load_tables` 合并执行：**与 Suonasi 重复的 id 一律取 Suonasi 值**
  （两表重叠 111 个 id），主观表只补 Suonasi 未覆盖的 **37** 个 id；合并后社区定数表共 **442** 张。
- **主观表当下限**（`_table_with_floor`）：该表自述「不会对 18.60 及以上进行定数」，其高难端被压缩在 18.59 以下，
  无法表达顶部；D\* 是连续模型，更高时取 D\*。实测**只升 7 张、不降任何谱**：
  #22206 18.56→20.00、#39209 18.59→19.84、#30942 18.56→19.34、#14480/#36301/#25523/#26017 小幅上调。
  单文件版由 `scripts/build_standalone.py` 离线复现同一规则（无缓存特征时保留表值并计数）。
- 主观表由 `scripts/build_subjective_diff.py` 从 xlsx 解析：丢弃"上架谱编号"为 `/` 的本地谱（24 行），
  表内无重复 id。校验：`scripts/verify_subjective.py`。
- 高难端**没有**系统性低估：残差 vs `log_duration` 相关 +0.06，最长档平均 +0.79（`scripts/diag_length.py`）。
- `data/anchors.json`（旧 OCR 集）仅在上述两表都不存在时才启用。

## 五、D\* 的 19 个谱面特征

`D* = bias + Σ wᵢ·(xᵢ − μᵢ)/σᵢ`，系数取自 `data/difficulty_model.json`。
前 16 个是提取出的客观特征；第 17 个 `le_hinge` 是**派生饱和项**。

**进入模型前有两道输入护栏**（`phira_pp.difficulty.prepare_features`）：
1. **clip**：每个特征先裁剪到**训练集观测区间**（存于模型 JSON 的 `clip`）。否则单张谱会无界外推——
   #54540 的 `chord_max`=7346 而全库上限只有 170（z=+736），光这一项就 +28.4。区间内的谱完全不受影响。
   **其中两个密度特征的上界再按「标签不再上升」收紧**：`nps_peak ≤ 50`、`chord_max ≤ 12`
   （实测标签：`nps_peak` 30-40 档 16.63、≥50 档 17.10、≥100 档反而 16.71；`chord_max` 10-20 档 17.10、≥15 档 16.36）。
   超出部分属堆叠/瞬移产物，不是难度。
2. **物量饱和 hinge**：`le_hinge = max(0, log_eff − 3.4)`。定数随物量上升到 `log_eff`≈3.4 后就不再上升
   （分档均值 17.10 → 17.88 → 17.83 → 18.20 → 17.76），而 `log_eff` 权重最大（+1.43），
   会把「键数最多」的谱一律顶到 ~20（其自身标签只有 ~18.6）。加 hinge 后拟合权重为 **−0.1202**（负=饱和，与数据方向一致）。

效果：CV **0.849 → 0.859**、nested **0.841 → 0.854**、in-sample RMSE **0.637 → 0.606**；
`#54540` 40.47 → **19.16（回到可计分且不虚高）**、`#3007` 20.60 → 19.77、`#31028` 20.33 → 19.69。
全库越界谱 3 → 2 张。

4. **手型/可达性**（`hand_step_p95`）：四指最近邻分配（`_hand_stats`），`FINGER_REST=[-0.75,-0.25,0.25,0.75]`、
   `FINGER_MAX_SPEED=13.05`（参考方案标定值，x 单位同为「半屏宽=1」，可直接沿用）。
   前向选择（`scripts/exp_hand.py`）CV **0.861 → 0.865** 采纳；`hand_speed_p95` 0.863、`hand_overreach_frac` 0.860 未采纳。
   生产重训：CV **0.859**、nested **0.854**、in-sample R² 0.875 / RMSE **0.606**（949 张）。

**关于「时长」项（审计 4）—— 数据不允许把它改成正值**。三种处理实测（同一训练集 / 同折 / α=30 固定）：

| 时长处理 | CV R² |
|---|---|
| 保留（拟合出 **−0.3623**） | **0.865** |
| 删掉（参考方案的做法） | 0.848 |
| 强加正耐力系数 λ=0.1 / 0.2 / 0.3 | 0.840 / 0.831 / 0.820 |

⚠️ **负系数的含义不是「越长越简单」**——它固定的是**总物量**，即「同样的按键数摊到更长时间 = 更稀疏 = 更简单」。
**同密度下变长，我们的模型是变难的**：时长 ×2 且密度不变时，`log_eff` +0.301（z=+1.14）贡献 **+1.34**，
`log_duration` +0.301（z=+1.91）贡献 **−0.73**，**净 +0.61**。（此前「−0.38 越长越简单」是我不准确的简写，特此更正。）

3. **分段（最难 10s 窗）聚合**（`seg_nps_p90`，`_SEG_SIZE=10s / _SEG_STEP=5s` + 末尾对齐窗）：
   参考实现（PPSR）的第一主轴，占其模型分裂 34.6%。前向选择（`scripts/exp_segment.py`）：
   带上限后 CV **0.859 → 0.861** 采纳。**它的意义不只是 +0.002**：`seg_nps_p90` 权重 **+0.3707**（第 4 大），
   同时把 **`log_eff` 的权重从 1.3980 压到 1.1765（−16%）** —— 「物量」不再单独承担难度。
   ⚠️ 它必须与 `nps_peak` 用**同一条密度上限（≤50）**：不加限时它会把 `#54540` 推到 22.30（51 秒纯爆发，段密度爆表），
   加上限后 `#54540` = 19.44 正常。其余候选（`seg_nps_p50` 0.856 / `seg_nps_max` 0.860 /
   `seg_speed_p95_mean` 0.860 / `seg_speed_p95_max` 0.861）未被采纳。

**显式专家覆盖层**（`data/difficulty_override.json`，优先级高于整条定数链）：D\* 是对定数标签的**最小二乘拟合**，
对标签为 18.4/18.56 的谱**永远不可能输出 19.4** 而不破坏其余谱的拟合——所以「故意偏离」是**策略决定**，
必须显式声明（参考实现 PPSR 也是这么处理 `#39209` 的：全库唯一一条人工 override = 19.395）。
当前两条：`#22206 = 19.40`、`#39209 = 19.60`（项目主给定）。

## 六、物量按按键类型加权（进入 `log_eff`）

| 键型 | 权重 | 判据 |
|---|---|---|
| `tap` | 1.00 | 基准 |
| `long`（hold ≥ 0.15 s） | 1.05 | 占手指更久 |
| `short`（hold < 0.15 s） | 0.95 | "点一下就抬起"，**低于 tap** |
| `flick` | 0.60 | |
| `drag` | 0.50 | 最低 |

- 顺序 `long_hold > tap > short_hold > flick > drag` 来自专家判断：Phira 的 hold **没有尾判**，
  只相当于「占一根手指的 tap」；短到可点一下就抬起的短长条应略低于 tap。
- 权重的**量级**来自 CV 网格搜索（`scripts/fit_type_weights.py`）；
  `SHORT_HOLD_SEC = 0.15` 取自实测 175,394 个 hold 时长的 p40（`scripts/probe_hold_weights.py`）。
- 与原始按键计数相比 CV 无差异（`scripts/ab_logeff.py`：0.837 / nested 0.821 vs 0.836 / 0.817），
  即这一改动不牺牲拟合精度。
